## Publication checklist

Before final publication:

1. Verify the exact PR head, its remote CI result, the warning disposition, and the explicit scope of any unverified target integrations. Obtain final release approval.
2. Prepare the approved publication-state documentation with the intended release date. Update README, changelog, wiki Home/status/installation/release pages, sidebar labels, and candidate baselines together. Keep dated acceptance reports historical. Replace candidate branch links with the final tag where appropriate. Validate and review that exact final diff before merging or publishing it.
3. Merge the reviewed candidate and verify CI on the resulting main commit. Update the draft's target to that exact merge SHA; do not leave it pointing at a mutable feature branch. Hold the separate public wiki update until the release is available.
4. Create the approved annotated `v1.2.0` tag, verify its resolved commit, and publish the prepared release notes against it. Do not publish internal preparation checklists as user-facing release notes.
5. Verify the GitHub release, Packagist version and source/dist reference, and downloaded archive against the tagged tree before claiming distribution is complete.
6. Copy the reviewed wiki sources to the separate wiki checkout, review and commit that exact diff, obtain the required publication approval, then push and verify the live Home, release page, sidebar, links, and images. Follow [Wiki maintenance](../WIKI-MAINTENANCE.md). A module push alone does not publish the wiki.

External provider ingestion, customer transfer destinations, consent-managed tag delivery, Varnish, native Nebula UI Bridge rendering, original Rocket Web package coexistence, and production-catalog capacity remain qualified as described in the local acceptance record. A release must not silently turn those unverified states into support claims.
